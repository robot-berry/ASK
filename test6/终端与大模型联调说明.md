# 解题宝终端与大模型联调说明

更新时间：2026-08-28

本文给大模型、服务端和终端固件队员共同使用。重点说明当前终端已经具备的能力、服务端必须遵守的接口/图片约定，以及如何解决答案页面尺寸不统一的问题。

## 1. 当前终端状态

硬件和显示参数：

- 主控：AC792N / WL83
- 摄像头：SC1346 MIPI，原生拍照 `1280×720`
- LCD：逻辑分辨率 `800×480`
- JPEG：`VIDEO_HIG_Q` 高质量，拍照缓冲区 `1 MiB`
- 实时取景：硬件视频链路，实测约 `29～30 fps`
- 全程不依赖 SD 卡，JPEG 和 PNG 均在 RAM 中处理

当前固件已经实测：

- K2 冻结拍照成功，JPEG 可达到约 40～80 KiB
- K3 从冻结页返回实时取景
- K4 在冻结页上传成功，服务器返回 HTTP `202`
- 服务器任务完成后，六张 PNG 下载、字节数、PNG 头和 SHA-256 校验成功
- 连续 K2 → K3 → K2 不再因为 LVGL 帧缓冲和 720p 拍照缓冲争用而复位

## 2. 正确的用户操作流程

| 状态 | 按键 | 行为 |
|---|---|---|
| 实时取景 | K2 | 停止视频，拍摄一张 1280×720 高质量 JPEG，进入拍照预览页 |
| 拍照预览页 | K3 | 隐藏旧照片，返回实时视频，进入下一次取景 |
| 拍照预览页 | K4 | 保留当前 JPEG，启动 HTTPS 上传和大模型解题 |
| 实时取景 | K4 | 不上传，按键会被终端拦截；需要先按 K2 冻结，再按 K4 |
| 结果页 | K3/K4 | 手动上一页/下一页，六张结果不自动轮播 |

拍照预览页故意保留原来的说明布局：左侧显示照片，右侧显示分辨率、`K3 Retake` 和 `K4 Upload`。服务端或结果页的显示优化不能破坏这个页面和按键语义。

## 3. 当前 HTTPS 接口约定

终端当前使用 HTTPS 和 Bearer 认证。Bearer token 属于部署密钥，不要写入本文或提交到代码仓库；服务端队员使用部署系统中的同一令牌即可。

### 3.1 能力检查

```http
GET /api/v1/capabilities
Authorization: Bearer <device-token>
Accept: application/json
```

终端期望 HTTP `200`，响应中至少应能确认 `api_version=v1`、`physics` 和 `math` 能力存在。

### 3.2 上传原始拍照 JPEG

```http
POST /api/v1/math/jobs/raw
Authorization: Bearer <device-token>
Idempotency-Key: <unique-key>
Content-Type: image/jpeg
Content-Length: <jpeg-bytes>
```

请求体就是终端拍摄的原始 JPEG，不要要求终端先 OCR、转 PNG 或上传到 SD 卡。终端会携带幂等键，网络重试必须返回同一个任务，而不能重复创建任务。

成功响应要求：

- HTTP `202`
- JSON 中包含 `job_id`
- JSON 中包含 `poll_url`
- 建议同时返回 `Location` 和 `Retry-After`

### 3.3 轮询任务

终端按照 `poll_url` 发起 GET。常见状态：

```text
preprocessing → solving → rendering → completed
```

失败时返回 `failed` 和可读错误信息。可以返回 `retry_after_seconds`，终端会限制在 1～10 秒范围内；不要要求终端固定 8 秒自动播放，当前结果页是用户手动翻页。

### 3.4 完成响应和六张图片

`completed` 响应必须提供下面六个固定文件名对应的元数据：

```text
01_question_knowledge.png
02_guidance_elite.png
03_guidance_upper.png
04_guidance_middle.png
05_guidance_lower.png
06_guidance_novice.png
```

每个文件至少包含：

```json
{
  "filename": "01_question_knowledge.png",
  "url": "/.../01_question_knowledge.png",
  "bytes": 12345,
  "sha256": "64-character-lowercase-hex"
}
```

终端下载每个 URL 后会校验：HTTP `200`、`Content-Type: image/png`、Content-Length、PNG 签名、IHDR、SHA-256、颜色格式和内存可解码性。校验失败的图片不会显示。

## 4. 必须统一的答案图片规格

### 推荐的最终规格

六张 PNG 必须统一为：

```text
宽度：800 px
高度：440 px
颜色：8-bit RGB 或 RGBA
交错：non-interlaced
背景：白色或高对比度纯色
```

`800×440` 是 LCD 中用于答案内容的区域；屏幕剩余约 40 px 用于顶部页码/按键提示。答案 PNG 本身不要再放 K3/K4 操作提示，也不要依赖滚动条。

### 为什么必须统一尺寸

终端会保持图片比例并把图片放进 `800×440` 内容区。若服务端返回不同高度，终端只能在以下方案中选择其一：

- 保持内容完整：图片两侧或上下留白；
- 强制铺满：拉伸文字/公式；
- 中心裁剪：可能裁掉答案内容。

当前实际联调曾收到：

```text
800×584
800×779
800×829
800×1048
```

这些图片宽度正确，但高度不统一，所以第一张/长页面看起来不像 `800×440` 横屏答案页。这个问题的根因在服务端渲染输出，不是 JPEG 拍照失败。终端已经增加小图实际放大能力，但不能在不裁切或不拉伸的情况下把 800×1048 变成 800×440。

## 5. 大模型结果渲染建议

建议服务端采用“两阶段”流程：

1. 大模型先输出结构化解题结果：题目要点、知识点、步骤、公式、结论。
2. 独立的横屏渲染器把结构化结果排版到固定 `800×440` 画布。

六页保持以下语义和披露边界：

1. `question_knowledge`：本地 OCR 重排的原题，不依赖模型生成。
2. `guidance_elite`：只问，不给知识点、公式、方法或方向。
3. `guidance_upper`：只点知识域，不说明如何应用。
4. `guidance_middle`：只点破关键观察或第一步，不继续展开。
5. `guidance_lower`：给编号解题骨架，不展开冗长运算，并保留作答空白。
6. `guidance_novice`：公式卡与兜底详解，但最终代入、运算或结论仍留给学生。

排版规则建议：

- 安全边距至少 24 px，正文不要贴边。
- 公式使用清晰的数学字体或 SVG/高质量栅格化结果。
- 每页控制行数，内容过长要在页与页之间重新分段，而不是生成超过 440 px 的长图。
- 页与页之间必须衔接，例如第 2 页末尾明确“下一页继续代入/化简”。
- 不要把手机竖屏长截图直接转成 PNG；要在服务端重新排版成横屏页面。
- 生成后服务端必须再次检查最终 PNG 的实际 IHDR 尺寸，不能只检查 HTML/CSS 容器尺寸。

推荐在完成响应中增加可选字段，方便联调和追踪：

```json
{
  "render_version": "answer-landscape-v1",
  "canvas": {"width": 800, "height": 440},
  "pages": 6
}
```

终端当前不会依赖这些可选字段，仍以 PNG IHDR 为准。

## 6. 终端固件相关代码

主要文件：

- `sdk/apps/wifi_soundbox/mode/net_music/solver_camera_ram_test.c`：K2 拍照、K3 重拍、K4 上传、任务线程和内存生命周期。
- `sdk/apps/wifi_soundbox/mode/net_music/solver_https_client.c`：HTTPS 能力检查、JPEG 上传、任务轮询、六张 PNG 下载与校验。
- `sdk/apps/wifi_soundbox/ui_action.c`：拍照预览页、结果页、结果图片缩放、K3/K4 导航。
- `sdk/apps/wifi_soundbox/include/app_config.h`：服务端主机和接口路径配置。
- `sdk/apps/common/lvgl_v8/examples/porting/lv_port_disp.c`：LVGL 暂停/恢复和 framebuffer 生命周期。

结果页当前使用 LVGL 的实际图片尺寸模式，并按 `800×440` 计算缩放；不要为了让长 PNG 铺满而简单改成无条件裁剪。

## 7. 联调验收清单

服务端发布新渲染器前，建议用真实终端完成以下检查：

- [ ] `/api/v1/capabilities` 返回 HTTP `200`。
- [ ] JPEG 上传返回 HTTP `202`、`job_id` 和 `poll_url`。
- [ ] 相同幂等键重试不会创建重复任务。
- [ ] 任务状态能从处理中进入 `completed` 或明确 `failed`。
- [ ] 六个固定文件名全部存在。
- [ ] 六张 PNG 的实际 IHDR 均为 `800×440`。
- [ ] 六张图片为 non-interlaced PNG，字节数和 SHA-256 与元数据一致。
- [ ] 终端 K2 → K4 可以完成上传和结果显示。
- [ ] 结果页 K3/K4 手动翻页，不能自动轮播。
- [ ] K2 → K3 → K2 连续循环至少 3 次无复位、无 `malloc` 失败。
- [ ] 结果页不出现 LVGL 滚动条，数学公式和中文文字清晰可读。

## 8. 当前最重要的协作结论

终端侧链路为“实时取景 → 拍照预览 → 上传 → 轮询 → 六图显示”。服务端和终端必须同时采用上述六个固定文件名；仍写死四页数组的旧固件需要先扩展到六页。服务端将六张结果固定为 `800×440` 后，终端无需裁剪答案内容即可统一铺满显示。
